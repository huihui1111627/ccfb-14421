# ClockQL — 拍卖查询前端

花卉拍卖市场按降价钟（Dutch clock）成交，交易员和分析员用 SQL 查成交价。这个仓库是一个**独立的查询前端**：只负责把 SQL 变成逻辑计划交给已有执行端，本身不存储、不调度、不做分布式执行。随附一个最朴素的逐行解释器，只为验证改写正确性，以及一个展示解析与改写全过程的网页。

```
SQL 文本
  ├─ 词法分析     internal/engine/lexer.go     带行列号，坏字符不中断
  ├─ 语法分析     internal/engine/parser.go    优先级爬升 + 多错误同步恢复
  ├─ 名字绑定     internal/engine/binder.go    CTE / 相关子查询 / LATERAL / 歧义
  ├─ 类型推导     internal/engine/types.go     定点小数、整数、日期、钟面刻度
  ├─ 逻辑计划     internal/engine/plan.go      节点 schema 即对外契约
  ├─ 规则改写     internal/engine/rules.go     跑到不动点，逐次校验 schema
  └─ 参考解释器   internal/engine/eval.go      逐行嵌套执行，只用于验证
```

## 运行

```sh
go build ./...
go test ./...

# 差分验证：随机生成合法/错误查询，跑改写前后并比对
go run ./cmd/verify -valid 20000 -bad 6000 -datasets 3 -json /tmp/verify.json

# 检查页面
go run ./cmd/server -addr 127.0.0.1:8765 -verify-json /tmp/verify.json
```

网页分六块：**语法树**（规范化后的 AST）、**名字绑定结果**（输出列、类型、来源、CTE
引用次数）、**报错列表**（行号列号、错误码、阶段、修复提示）、**词法记号**、
**每条改写规则前后的逻辑计划**（含触发/检查/拒绝计数和逐节点差异）、
**按轮次的计划快照**，以及**执行结果**（改写前与改写后并排，并给出是否完全一致）。

## 1. 词法与语法

- 自己写的词法器，位置按 **1 基行号 + rune 列号** 计；未闭合字符串/注释、非法字符
  都记为诊断，不中断词法流。
- 表达式按**运算符优先级与结合性**用优先级爬升法解析：`OR` < `AND` < `NOT` <
  比较/`IS`/`LIKE`/`IN`/`BETWEEN` < `+ -` < `* / %` < 一元 `-`。同一层的算术与
  比较都左结合，打印时只在必要处加括号。
- **一处语句内多处语法错误**：语法错误不会抛出，而是记录后按层次恢复——
  select 项、FROM 项、JOIN 项、每个子句的表达式各自有恢复点。恢复会跳过损坏片段，
  在 `AND`/`OR`/逗号/闭括号/下一个子句处重新尝试解析，因此同一句里的多处独立错误
  会**一次全部报出**。
- 为避免"级联报错"，绑定阶段会记住语法错误恢复到达的最远位置：**损坏区间之内**的
  语义错误（未知列、类型不符、参数个数）是语法损坏的后果，予以抑制；**损坏区间之后**
  的错误照常报告。因此 `SELECT lot_id, FROM lots WHERE stems > AND grade =`
  恰好给出三个语法错误，不会再多出五条派生错误。

## 2. 名字解析

- **公用表表达式**：`WITH`，可选列名清单，`RECURSIVE` 语法接受。CTE 先于同名的
  目录表解析。每次引用生成一个 `CTEScan`，并统计引用次数。
- **相关子查询**：列引用沿作用域链向外查找，最近一层命中优先（SQL 作用域规则）。
  `ColRef.Depth` 记录跨越的层数，解释器用 `Env.Outer` 逐层取行。
- **侧向连接**：`JOIN LATERAL (...)` 的派生表能看到同一 FROM 中左侧已绑定的列；
  非 LATERAL 的派生表只能看到外层作用域。
- **歧义**：同一作用域内同名列有多个候选时报 `ambiguous`，**并列出全部候选**
  （`l.lot_id, t.lot_id`）以及如何限定。跨作用域的重名不算歧义。

## 3. 类型推导

| 类型 | 说明 |
|---|---|
| `int` | 整数，运行时溢出报错 |
| `decimal(p,s)` | 定点小数，最多 18 位有效数字 |
| `tick(0..100.00)` | 钟面刻度，内部按 0.01 的整数存储 |
| `date` | 公历日期，按天存储 |
| `string` / `bool` | |

定点运算的类型规则（结果类型由类型推导决定，运行时按其 scale 舍入）：

- `+ -`：`p = max(p1-s1, p2-s2) + max(s1,s2) + 1`，`s = max(s1,s2)`（进位位）。
- `*`：`p = min(p1+p2, 18)`，`s = min(s1+s2, 10)`。
- `/`：`s = max(6, s1, s2)`，`p = 18`；`int / int` 仍为整数（截断）。
- `%` 只接受整数；小数取余请用 `round_to`。
- 舍入一律**四舍五入、远离零**（`1.25 → 1.3`，`-1.25 → -1.3`）。

**日期与钟面刻度必须显式转换**：

- `to_clock(date, base)` → `tick`：日期距基准日的天数 × 100，超出 101 天窗口报错。
- `from_clock(tick[, base])` → `date`：逆转换。
- 隐式混用一律报 `implicit-conversion` 错误并提示这两个函数，例如
  `WHERE base_tick = 95.00` 或 `WHERE sold_date = 1`。
- 写常量必须显式：`95.00::tick` 或 `TICK '95.00'`；`DATE '2024-01-01'`。
  常量向上转型在绑定期求值，`100.15::tick`（超过最大值 100.00）直接报错。

## 4. 改写规则

| 规则 | 前置条件 | 作用 |
|---|---|---|
| `constant-fold` | 表达式不含列、聚合、子查询引用；求值不报错 | 在计划期求值 |
| `outer-to-inner` | 连接是 LEFT/RIGHT/FULL，且其**上方**过滤条件在空值扩展行上**不可能为真** | 降为 INNER（FULL 可降为 LEFT/RIGHT） |
| `simplify-false` | 过滤条件（或内连接 ON）含可证伪的合取项 | 整个子树换成同 schema 的空关系 |
| `inline-cte` | 该 CTE 在全计划中**恰好被引用一次** | 直接把体展开进去（用 `Rename` 保持列名与限定符） |
| `cnf` | 合取范式项数不超过 64 | 过滤条件转 CNF；超限则**放弃转换**并给出提示 |

`outer-to-inner` 用三值逻辑的可能性集合判断，而不是语法匹配：只有谓词在空值扩展行上
**取不到 TRUE** 时才降级。因此 `t.x IS NULL` 和 `NOT (t.x IS NOT NULL)` 会**保留**
外连接（它们恰恰选中空值扩展行），`t.x IS NOT NULL`、`t.x > 1`、`NOT t.b` 才会降级。
这条规则最初写成"遇到 NOT 就降级"，被随机数据测出了错误（见"验证"一节）。

## 5. 跑到不动点

`Rewrite` 每一轮依次对整棵树自底向上应用全部规则；只要有任何节点变化就再来一轮，
最多 12 轮。每轮结束后**校验根节点输出 schema**（列名、类型、限定符、可空性）：
被违反的轮次整体丢弃并记一条 `rewrite` 警告。规则内部也不可变改输入树，只返回新树。

## 6. CNF 与项数上限

转换前先按结构估算项数（`AND` 相加，`OR` 相乘）；超过 `MaxCNFTerms = 64` 就**保持
原样**，并在警告列表里给出"CNF skipped: estimated terms exceed 64"。页面上能看到
这条警告以及该规则"检查 2 次、拒绝 1 次"的计数。

## 7. 拍卖专用函数

函数用统一的注册表：`RegisterFunction(name, args, variadic, ret, fn)`。
`RegisterBuiltins` 与 `RegisterAuction` 走的是**同一个入口**，类型检查也走同一份
`FnSig.CheckArgs`。内置的拍卖函数：

| 函数 | 说明 |
|---|---|
| `tick_round(t)` | 取整到整个刻度单位 |
| `tick_bucket(t, step)` | 向下对齐到 step 个刻度 |
| `tick_span(a, b)` | 两刻度的距离，`decimal(5,2)` |
| `price_to_cent(t)` | 刻度转整数分 |

宿主可以用同样的方式注册自己的函数（见 `TestAuctionFunctionsRegisteredLikeBuiltins`，
其中注册了自定义函数并验证了同一套类型检查会拒绝错误参数类型）。

## 8. 参考解释器

`Evaluator` 是最朴素的逐行嵌套执行：每个计划节点物化成 `[]Row`，连接是双重循环，
子查询对每一行重新执行。它**没有**任何优化——这正是它能作为"改写正确性基准"的原因。
NULL 三值逻辑、重复行、小数 scale 都按原样保留。

## 验证

`cmd/verify` 做两件事：

**合法查询的差分测试。** 随机生成覆盖每条规则、每种语法形状的查询（含 CTE、连接、
聚合、集合运算、相关子查询、CAST、IN/NOT IN、LIKE、BETWEEN、DISTINCT、ORDER BY
…）。每条查询生成三份随机拍卖数据（含 NULL、重复行、小数舍入、钟点边界），分别用
改写前和改写后的计划执行，**结果多重集必须逐值相同**——小数比较区分 scale
（`1.50` 与 `1.500` 必须一致，且改写不得改变输出 scale），NULL 与任何字面量不同，
重复行按出现次数比较。同时校验输出 schema 不变。

**错误查询的期望位置比对。** 一半由合法查询注入故障（多余逗号、多余 `=`），
一半是人工写好、带有精确期望位置与错误类别的用例（缺操作数、未闭合函数、类型不符、
隐式转换、歧义列、未知表、非布尔 WHERE、嵌套聚合、钟面常量越界……），每条都附带
一条**必须能干净绑定**的正确版本作为对照。判定标准：期望的每个位置都要有对应诊断，
且**不允许多余诊断**。

### 验证发现过的真实缺陷

差分测试不是走形式，它抓到了几个单靠手工用例不会发现的问题：

1. **外连接降级不健全**：`NOT (t.x IS NOT NULL)` 会选中空值扩展行，原实现一见 `NOT`
   就降为内连接，结果少了几行。改为三值逻辑可能性分析后修复，并补了反例测试。
2. **`NOT IN` 三值语义**：原本把"子查询含 NULL 且未命中"算成 FALSE，正确是 UNKNOWN。
3. **`DISTINCT` 位置错误**：原计划在投影之前去重，对多列投影会多出重复输出。
4. **HAVING 未重定位聚合槽位**：`HAVING count(*) > 1` 读错了列。
5. **常量越界转型**：`100.15::tick` 只在某行执行到时报错，改写会改变哪些行走到它；
   现改为绑定期求值并报错。
6. **函数套聚合**：`round_to(avg(x), 2)` 被误判为嵌套聚合，只有真正的
   `count(sum(x))` 才该报错。
7. **LATERAL 连接未按行求值**：解释器把相关的派生表只算了一次，导致
   `correlation depth exceeds` 错误；现在相关的一侧对每个左行重新求值，
   并新增了 `JOIN LATERAL` 与标量相关子查询的逐行语义测试。

## 已知边界

- 集合运算不做类型提升：`UNION` 两侧列类型必须完全一致（含 decimal 精度），否则报错。
- 递归 CTE 只做语法与绑定接受，不做递归求值（本前端不负责执行语义扩展）。
- 不带 `FROM` 的 `SELECT` 支持，但 `SELECT 1 WHERE ...` 的列引用只能来自外层作用域。
- `LIKE` 只支持 `%` 与 `_`，无转义字符。
- 相关的右侧（LATERAL）只支持 INNER/LEFT 连接；与 RIGHT/FULL 组合会在执行期
  明确报错而不是给出错误答案。
- 解释器按"每行重算子查询"的最朴素方式执行，遇到爆炸性连接会触发行数上限保护
  （仅用于验证，不追求性能）。
